# Design

## Context

Ver `proposal.md` - Why. Estado actual: el esquema de Supabase ya tiene `generation` (con `status` en `generating`/`ready`/`done`/`error`) y `exercise` (con `saved`/`deleted_at`) aplicados y sin usar todavia — nadie los escribe. El backend FastAPI solo tiene auth (`esqueleto-monorepo-auth`). `docker-compose.yml` solo trae `frontend`, `backend` y `litellm`; `litellm` ya expone el modelo logico `generator` resuelto por variables de entorno (seccion 11 de la especificacion), que el usuario ya ha configurado con OpenRouter.

## Goals / Non-Goals

**Goals:**
- Que los tres agentes de generacion corran como servicios A2A reales, orquestados por FastAPI, con memoria persistente y trazas en Langfuse.
- Reutilizar `generation`/`exercise` tal como estan; no son necesarios cambios de esquema en `public`.
- Mantener `service_role` exclusivo de FastAPI (seccion 11 de la especificacion): el agente de ejercicios NO debe usarlo para consultar `exercise`.

**Non-Goals:**
- Guardar ejercicios candidatos como definitivos, bloques, asignaciones, evaluador/revisor (paso 3).
- Cualquier pantalla de frontend para lanzar o ver una generacion.
- Preparacion/subida del repositorio en si (clonado, extraccion de zip): se asume que, al llegar al orquestador, el repo ya esta en una carpeta local legible; como se prepara esa carpeta es un detalle de implementacion de las tareas, no un requisito de spec nuevo.

## Decisions

**Los tres agentes son procesos Python separados (`agents/web/`, `agents/code/`, `agents/exercises/`), cada uno su propio servicio A2A con `a2a-sdk`.** Alternativa considerada: un unico proceso que sirva los tres "agentes" como rutas distintas. Se descarta porque la especificacion (seccion 7) los define como servicios A2A independientes con su propia Agent Card — mezclarlos en un proceso rompe el aislamiento de fallos que pide la seccion 7 (que falle el de codigo no debe poder tumbar al web) y complica los limites de tiempo por tarea.

**Los agentes llaman al modelo `generator` via el proxy HTTP de LiteLLM ya existente (`http://litellm:4000`), con un cliente OpenAI-compatible (`langchain-openai`), autenticados con `LITELLM_MASTER_KEY`.** Alternativa considerada: que cada agente use el SDK de `litellm` directamente con `GENERATOR_MODEL`/`GENERATOR_API_KEY` propios. Se descarta: duplicaria en cada agente la resolucion de proveedor que `infra/litellm/config.yaml` ya centraliza, y expondria la clave real de OpenRouter en tres contenedores en vez de uno. Con el proxy, los agentes solo necesitan la URL interna del servicio y la master key.

**Memoria en un esquema `memory` nuevo de PostgreSQL, con conexion directa (no via PostgREST/`service_role`), usando un rol `agents_memory` de solo ese esquema.** `langgraph-checkpoint-postgres` (`PostgresSaver`+`PostgresStore`) exige una conexion Postgres nativa; no hay forma de usarlo a traves de la API REST de Supabase. El rol `agents_memory` SHALL tener `USAGE`+`CREATE` solo sobre `memory`, nada sobre `public`, para que una fuga de sus credenciales no exponga datos de alumnos ni ejercicios.

**`search_saved_exercises` usa un segundo rol de Postgres, `agents_exercise_reader`, con `SELECT` solo sobre `public.exercise`, en conexion directa — no `service_role`.** La especificacion original reserva `service_role` para FastAPI (seccion 11); darselo al agente de ejercicios lo convertiria en un segundo punto con acceso total a la base de datos. Un rol de solo lectura sobre una sola tabla es coherente con el principio de RLS como segunda capa ya establecido en `esqueleto-monorepo-auth` (aunque aqui no hay RLS de por medio, sino permisos de rol de base de datos, porque quien llama no es un usuario de Supabase Auth).

**El servicio A2A de prueba es desechable: se ejecuta en local para validar el SDK, no se añade a `docker-compose.yml` ni queda como servicio permanente.** Alternativa considerada: dejarlo como cuarto servicio de ejemplo. Se descarta por ruido: añadiria un servicio mas a mantener sin aportar comportamiento que la spec necesite; su unico valor es confirmar pronto, antes de escribir los tres agentes reales, que `a2a-sdk` y el cliente A2A de FastAPI encajan como se espera.

**Limites de tiempo con `asyncio.wait_for` en el orquestador de FastAPI, no en los propios agentes.** Cada llamada A2A sincrona se envuelve en un timeout de 2 minutos; la generacion completa, en uno de 5 minutos medido desde que se crea. Alternativa considerada: que cada agente se autolimite internamente. Se descarta: el orquestador es quien conoce el tiempo ya transcurrido de la generacion completa y es el unico sitio donde aplicar el limite de 5 minutos tiene sentido; duplicar logica de timeout en cuatro sitios (orquestador + 3 agentes) es mas fragil.

**No hay cambios de esquema en `generation`/`exercise`.** Ambas tablas, aplicadas en `esqueleto-monorepo-auth`, ya tienen las columnas que este change necesita (`status`, `error_message`, `kind`, y en `exercise` el candidato con `saved = false` por defecto). Solo hace falta la migracion nueva para el esquema `memory` y los dos roles.

## Patron de cableado A2A confirmado (tarea 2.2)

El servicio de prueba desechable (`a2a-sdk` 1.2.2, instalado y probado en esta sesion) confirmo lo siguiente, a reutilizar tal cual en `agents/web/`, `agents/code/` y `agents/exercises/`:

- **Los tipos son protobuf, no pydantic.** `a2a.types.AgentCard`, `Message`, `Part`, etc. vienen de `a2a.types.a2a_pb2`. Construirlos a mano o, mejor, usar los helpers de `a2a.helpers.proto_helpers` (`new_text_message`, `new_data_message`, `get_message_text`, `get_stream_response_text`...) en vez de instanciar protobufs directamente.
- **Instalar con el extra `fastapi`** (`a2a-sdk[fastapi]`) mas `fastapi` y `sse-starlette` explicitos — el extra no arrastra `sse-starlette` como dependencia transitiva resuelta y el import falla en caliente (`a2a.compat.v0_3.jsonrpc_adapter`) si falta.
- **Servidor:** `AgentExecutor.execute(context, event_queue)` hace `await event_queue.enqueue_event(new_text_message(...))` para una respuesta inmediata (sin Task de larga duracion, que es nuestro caso: los tres agentes responden una vez y terminan). `DefaultRequestHandler(agent_executor, task_store, agent_card)` con `InMemoryTaskStore()` basta. Las rutas se montan en FastAPI con `add_a2a_routes_to_fastapi(app, agent_card_routes=create_agent_card_routes(card), jsonrpc_routes=create_jsonrpc_routes(handler, rpc_url="/"))`; la Agent Card queda servida automaticamente en `/.well-known/agent-card.json`.
- **Cliente (a reutilizar en el orquestador FastAPI, tarea 6.1):** `await create_client(url, ClientConfig(streaming=False))` resuelve la Agent Card solo y da un cliente sincrono; `client.send_message(SendMessageRequest(message=new_text_message(texto, role=Role.ROLE_USER)))` devuelve un iterador async de `StreamResponse` (una sola respuesta en modo no streaming); `get_stream_response_text(response)` extrae el texto sin mirar a mano si vino como `message` o `task`.
- **Metadatos y `trace_id`:** `RequestContext.metadata` expone `request.metadata` (nivel `SendMessageRequest`) como `dict`; `context.message.metadata` da los metadatos del propio `Message`. Para la tarea 3.6/4.5/5.5 (propagar `trace_id` de Langfuse), el mensaje A2A lo lleva en `message.metadata`, asi que se lee con `context.message.metadata.get("trace_id")` del lado agente, y se escribe pasando `metadata={"trace_id": ...}` a `new_text_message(...)` (o al `SendMessageRequest`) del lado orquestador.

## Contrato de entrada del agente de codigo (tarea 4.1-4.4)

El `Non-Goal` de arriba deja la preparacion del repo fuera de alcance, pero el agente de codigo necesita un contrato concreto para leerlo y para la clave de memoria. Decisiones tomadas al implementar el grupo 4, sin requisito de spec nuevo (son detalle de implementacion):

- **El mensaje A2A al agente de codigo lleva `repo_path` (string, ruta local legible desde el propio contenedor del agente) y `technologies` (misma lista que recibe el agente web), como parte de datos** (`{"repo_path": "...", "technologies": [...]}`), igual que `parse_technologies` en `agents/web/app/input.py`. Quien prepara esa carpeta (clonado, zip, lo que sea) es responsabilidad del orquestador (grupo 6) o de quien lo preceda; el agente de codigo solo la lee.
- **`list_files`/`read_file` resuelven toda ruta con `Path.resolve()` y comprueban que el resultado sigue dentro de `Path(repo_path).resolve()`** antes de leer nada (`relative_to()` lanza `ValueError` si se sale, que es como se detecta y rechaza — cubre `../`, symlinks que escapan, y rutas absolutas fuera del repo).
- **Clave de memoria larga (tarea 4.4): `sha256(f"{repo_identity}|{normalize_technologies(technologies)}")`**, donde `repo_identity` es `git rev-parse HEAD` combinado con `git remote get-url origin` cuando `repo_path` es un repo git (el caso real: la prueba de aceptacion del grupo 8 usa el repo real de Pokemon); si no es un repo git (sin `.git`, o sin remoto), cae a hashear el propio `repo_path` — degradacion aceptable porque ese caso no es el camino principal de la spec. Esto hace que la cache sobreviva a que el orquestador reclone el repo en una ruta temporal distinta entre generaciones, siempre que el commit no cambie — al reves que la memoria del agente web (clave = solo tecnologias), aqui la identidad del repo importa tanto como las tecnologias.
- **`docker-compose.yml` (grupo 7) monta el mismo volumen de repos preparados como solo-lectura en el contenedor de `agent-code`.** Para las verificaciones manuales de las tareas 4.1-4.5 (sin orquestador todavia), se usa una carpeta local cualquiera (un repo git real pequeño) pasada directamente como `repo_path`.

## Contrato de entrada/salida del agente de ejercicios (tarea 5.1-5.3, planificado antes de implementar)

La spec (`exercise-generation`) deja el contrato exacto fuera de su alcance (solo dice "tipo", "numero" y "resultados de web/codigo"); `public.exercise` si fija la forma de un ejercicio (`type` checked a `knowledge`/`debug` -- NO `both`, `statement`, `code jsonb default '[]'`, `expected_answer`). Decisiones para implementar el grupo 5, siguiendo el mismo criterio que el contrato del agente de codigo (4.1-4.4: decision documentada aqui antes de tocar codigo, sin requisito de spec nuevo):

- **Entrada A2A (parte de datos):** `{"exercise_type": "knowledge"|"debug", "count": 1-5, "web_result": {...}|null, "code_result": {...}|null}`. `web_result`/`code_result` son el `dataclasses.asdict()` tal cual de `WebResearchResult`/`CodeAnalysisResult` (los mismos dicts que ya produce cada agente) -- el orquestador (grupo 6) los reenvia sin transformarlos; evita inventar un formato intermedio y mantiene el agente de ejercicios desacoplado de como exactamente web/codigo construyen su resultado. `exercise_type` solo acepta `knowledge`/`debug` porque esa es la unica forma valida de `public.exercise.type`; `generation.kind` SI admite `both`, pero resolver ese caso (pedir dos tandas, una por tipo) es responsabilidad del orquestador (grupo 6), no de este agente -- un agente de ejercicios que solo sabe producir un tipo por llamada es mas simple y mas facil de probar.
- **Salida: `ExerciseGenerationResult(candidates: list[CandidateExercise], memory_hit: bool)`** (el `memory_hit` aqui es informativo/trazabilidad, igual que en los otros dos agentes, aunque la 5.4 diga "sin caducidad" -- no hay "cache-hit" que salte el trabajo entero como en web/codigo, porque cada generacion es nueva por definicion; lo que persiste entre llamadas es el *historial* de enunciados ya propuestos, no el resultado completo). `CandidateExercise`: `type` (echo del `exercise_type` pedido, para que el orquestador pueda insertar directo en `public.exercise` sin recomponer el campo), `statement` (enunciado), `code: list[{"file": str|null, "code": str}]` (codigo de apoyo; vacio para un `knowledge` sin codigo, con el cambio ya introducido para un `debug`), `expected_answer` (respuesta esperada) -- mapea 1:1 a las columnas de `public.exercise` que el orquestador movera a esa tabla cuando el tech lead guarde un candidato (fuera de alcance de este change, ver Non-Goals, pero el shape se elige pensando en esa escritura futura).
- **`search_saved_exercises` (tarea 5.2): una sola consulta por tarea en la implementacion inicial** (`SELECT id, statement, code, expected_answer FROM public.exercise WHERE type = $1 AND saved = true AND deleted_at IS NULL ORDER BY created_at DESC LIMIT 10`, rol `agents_exercise_reader`, conexion directa separada de `agents_memory` -- ver `infra/supabase/migrations/0003_agents_memory.sql`). El limite de "hasta 3 consultas por tarea" de la spec se implementa como techo de un `SearchBudget` reutilizable (mismo patron que `SearchBudget`/`FileBudget` de los otros dos agentes) para dejar sitio a una segunda/tercera consulta futura (p. ej. una por tecnologia relevante) sin cambiar el contrato del budget; no se usa mas de una consulta todavia porque ningun escenario de la spec lo exige y anadir mas round-trips sin un requisito concreto solo complica la tarea 5.3.
- **Evitar temas repetidos (5.3/5.4) se resuelve con DOS fuentes, ambas en el prompt de la llamada final al modelo:** (a) hasta 10 enunciados ya *guardados* de ese tipo via `search_saved_exercises`, y (b) hasta 20 enunciados ya *propuestos* (guardados o no) de ese tipo via la memoria larga propia del agente (tarea 5.4, clave = `exercise_type`, sin TTL, lista de los ultimos 20 enunciados que se va recortando por el principio al escribir). El modelo recibe ambas listas y se le pide explicitamente no repetir el tema de ninguna. Es una unica llamada al modelo (no el patron de dos pasos del agente de codigo): no hay aqui una fase de "elegir que leer" equivalente a `_pick_files`, asi que un solo prompt con enunciados+resultados+limites basta.

**Hallazgo (verificando el scaffold, tarea 5.1): toda parte de datos de un mensaje A2A viaja como protobuf `Struct`, cuyo unico tipo numerico es `double`.** Un entero real mandado por el llamador (`count=3`) llega al otro lado como `float` (`3.0`), nunca como `int` -- confirmado enviando un mensaje real a traves del dispatcher JSON-RPC del SDK (no es una peculiaridad del test, es como serializa el propio `a2a-sdk`). `app/input.py` lo tolera exigiendo un valor entero exacto (`float.is_integer()`) y convirtiendolo a `int` antes de devolverlo, igual que ya se toleraba `bool` (subclase de `int` en Python). **Aplica a cualquier campo numerico futuro en una parte de datos**, en particular el `count`/`numero` que el orquestador (grupo 6) reenviara a este agente y cualquier endpoint HTTP que lo reciba de un cliente real.

## Risks / Trade-offs

- [Conexion directa a Postgres desde tres agentes mas el backend añade conexiones fuera del pool que gestiona Supabase via PostgREST] → Mantener el pool de conexiones de cada agente pequeño (1-2), y si se vuelve un problema, pasar por el pooler de Supabase (pgbouncer) sin cambiar el contrato de las specs.
- [`a2a-sdk` es una dependencia nueva y poco probada en este proyecto] → El servicio de prueba desechable (primera tarea de este change) valida el cableado antes de construir los tres agentes reales sobre el mismo patron.
- [Si LiteLLM cae, los tres agentes de generacion fallan a la vez porque comparten el mismo proxy] → Ya es una dependencia compartida desde `esqueleto-monorepo-auth` (LiteLLM esta pensado como punto unico de acceso a modelos); no es un riesgo nuevo de este change.
- [Dos roles de Postgres nuevos (`agents_memory`, `agents_exercise_reader`) son credenciales adicionales que gestionar] → Alcance minimo por diseño (un esquema, una tabla de solo lectura); se documentan en `.env.example` igual que las demas.

## Migration Plan

Nueva migracion `infra/supabase/migrations/0003_agents_memory.sql`: crea el esquema `memory`, los roles `agents_memory` (USAGE+CREATE sobre `memory`) y `agents_exercise_reader` (SELECT sobre `public.exercise`), y sus contraseñas via variables de entorno de Supabase al aplicarla (no hardcodeadas en el SQL). Se aplica con `apply_migration` igual que las dos anteriores; no hay datos previos que migrar (greenfield). Las tablas de `langgraph-checkpoint-postgres` dentro de `memory` las crea el propio paquete al arrancar cada agente (`setup()`), no esta migracion.
